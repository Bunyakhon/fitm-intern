## Backup, restore and failure recovery

The backup CLI reads the configured source and independently verifies Docker's
source database OID, cluster system identifier and user before pg_dump. It uses
custom format with source sessions set read-only, binary-safe IO, exclusive file
creation and a SHA-256 manifest. Production archives must reside outside the repo
in a private, access-controlled folder. The manifest includes the source hash,
database/cluster identity, schema/ledger and row digests, plus independent restore
evidence. Installation requires its exact manifest SHA, intact archive, separate
restore cluster and age <24 hours, and rechecks the source baseline under locks.

Restore uses a newly generated `fitm-026-test-<16 hex>` container and
`fitm_026_restore_<16 hex>` database, ownership label `fitm.026.disposable`, isolated
PostgreSQL 16 and loopback-only port. It does not restore into intern_system or the
source cluster. pg_restore uses `--exit-on-error --single-transaction`. Cleanup
checks exact name, label and environment, then removes only its owned container
and anonymous volume. Synthetic archives are retained in named OS-temp folders;
paths, hashes and bytes are in the evidence. No production archive was made here.

Restore verification checks exact rows, ledger and structural catalog, functions,
enums and sequence state. PostgreSQL 16 reparses some CHECKs during pg_dump/restore
(e.g. casts applied to arrays versus individual elements). CHECK text hashes can
therefore differ. The tool reparses source CHECK expressions on temporary LIKE
tables in the disposable restore cluster and compares the server's resulting
expressions exactly. It retains boolean grouping; source/restored schema hashes
are separately recorded with verified semantic equivalence.

Recovery decisions:

- New controlled installation: DDL + ledger share one transaction. Any DDL,
  ledger or post-verification error rolls back both. Reconnect and run preflight
  before deciding whether to retry after a connection/commit uncertainty.
- Both exact tables and ledger present: verify, do not drop/reinstall. The core
  is idempotent and ordinary status recognizes 026.
- Legacy DDL committed but ledger absent: only **both exact, empty, owned tables**
  qualify. Make a fresh backup and independent restore for this ORPHAN_SCHEMA
  baseline, then use `recover-ledger` with target/hash/manifest approval gates.
  It validates schema and records only 026 through Umzug without repeating DDL.
- Partial tables, missing tables with ledger, changed schema/owner/ACL/collation,
  populated orphan: **BLOCKED for automatic recovery**, keep flags off and retain
  evidence. No automatic table deletion or ledger manipulation is supplied.
- Automatic `down` stays disabled. A Development archive restore/drop or changes
  to existing identities require a separate reviewed plan and authorization.

## Remaining risks and approval boundary

- PostgreSQL 16, public application schema, current-user ownership and normal
  deterministic collations are required. Other schemas/owners/grants stop rather
  than being changed automatically. Tested version: 16.15.
- Stop application writes during real backup/install. Row or schema drift since
  backup stops installation. Existing-table SHARE locks and ledger lock can briefly
  block writes; 5-second lock timeout and 60-second statement timeout limit waiting.
- Dump IO is bounded to 256 MiB; larger archives fail and need a separately reviewed
  streaming procedure. Private Windows ACLs/encryption are operational requirements
  for real account backups; POSIX mode 0600 alone does not enforce Windows ACLs.
- pg_dump covers database data, not external uploaded profile files or global
  server roles. This migration never changes those files. A full environment
  disaster restore needs their existing backup process and role availability.
- CASCADE follows the original proposal on real actor deletion. No actors are
  deleted by installation, linking or recovery. A populated orphan needs provenance
  review; no automatic adoption is offered.
- Real provider configuration, account policy approval and onboarding remain
  separate acceptance gates. Both actual feature flags stay off.
